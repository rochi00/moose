**PETSc Kokkos types in MOOSE.** MOOSE rejects an unprefixed `-mat_type`. The working options are
`-vec_type kokkos -u_sys_mat_type aijkokkos`, where `u_sys` is the linear system name. With these,
the matrix is `seqaijkokkos`, and PETSc's `-log_view` attributes 100% of the KSP vector and matrix
flops to Kokkos (OpenMP on this machine).

## 2. Correctness

Kokkos and CPU solution trajectories agree to at most about 1e-15 relative over 10-20 implicit
Euler steps (orthogonal hex, 12^3 and 64^3). This holds with default and with Kokkos PETSc types,
and for the mixed variant (Kokkos flux kernels + CPU time derivative).

Determinism over time:
- **12^3 hex, 4 threads:** repeated Kokkos runs differ from step 1 at about 3e-16, from the atomic
  accumulation, and stay at that level over 10 steps.
- **64^3 hex, 8 threads:** repeats were bitwise identical. On structured, natively ordered hex
  meshes, threads rarely collide on the same entry, consistent with the layout mini-app results.

## 3. Why the solve was serial

- With 1 MPI rank and default types, PETSc uses `VECSEQ`/`MATSEQAIJ`. PETSc's own kernels are not
  OpenMP-threaded: `--with-openmp` only enables threaded external libraries.
- `KOKKOS_NUM_THREADS` only affected MOOSE's Kokkos assembly.
- Switching PETSc to Kokkos types threads the solve through Kokkos/OpenMP.

## 5. Conclusions

1. **The linear solve dominates once each step is solved** (about 90% of a step with default
   types), so assembly speedups alone cannot move the step time much.
2. **PETSc Kokkos types thread the solve.** At 8 threads they are 1.6x (GMRES) to 2.2x (BiCGStab)
   faster in `KSPSolve`. On 1 thread they are 1.3-2.3x slower: per-operation Kokkos overhead on
   GMRES's many small vector operations and reductions.
3. **Solver choice matters as much as threading.** BiCGStab needs about half the iterations of
   GMRES(30) here and far fewer multi-vector reductions. Together with Kokkos types, step time
   drops 2.9x.
4. **The GEMV options for `VecMDot`/`VecMAXPY` did not help** on this backend (a 9-22% slowdown).
5. **Next bottleneck.** With the fast solve, assembly is about 28% of the step (45 ms), and the
   empty host linear FV loop is about 17 ms of it. Skipping that loop when all objects are Kokkos
   is the next easy win.
6. **This is the GPU path.** Kokkos PETSc types plus Kokkos assembly already run end to end with
   correct results here. On a GPU the same options keep the solve on the device. The design should
   default to these types and to a reduction-light Krylov method (section 8 of the detailed
   design).

## 7. Implemented: skip the host loop, precomputed matrix slots, no mixing by default

### Changes (branch `rc/kokkos_moose_navier_stokes`)

1. **No mixed linear FV systems by default.**
   - `LinearSystem::initialSetupKokkosLinearFV` (`KokkosLinearSystem.K`) now errors if a linear
     system contains Kokkos linear FV kernels or BCs together with non-Kokkos linear FV kernels or
     BCs. The error lists the offending objects.
   - New Problem parameter `allow_mixed_kokkos_linear_fv` (Kokkos builds only, default `false`)
     accepts the slower mixed assembly.
   - Systems with no Kokkos objects are unaffected.
   - The test `kokkos/fe-fv-interplay.mixing_fe_fv` sets the opt-out: its host `LinearFVSource`
     couples to an FE variable, which no Kokkos linear FV object can do yet.
   - New test `mixing_linear_fv_error` covers the error.
2. **Host loop skipped.** When every linear FV object of a system is a Kokkos object
   (`_all_linear_fv_objects_kokkos`), `LinearSystem::computeLinearSystemInternal` skips the
   `ComputeLinearFVElementalThread` / `ComputeLinearFVFaceThread` loops.
3. **Precomputed matrix slots.**
   - New `System::getMatrixSlot(row, col)` (host), `System::getMatrixValueAtSlot` / `Matrix::valueAt`
     (device), and `LinearSystemContributionObject::accumulateTaggedMatrixAtSlot`.
   - Flux kernels precompute two slots per directed internal side and one per boundary side;
     elemental kernels precompute one diagonal slot per block element. All of this is in
     `initialSetup`.
   - The matrix loops no longer search the CSR row.
   - **Pitfall found:** the Kokkos mesh moves its neighbor table to the device
     (`_elem_neighbor.moveToDevice()`, `KokkosMesh.K:419`), so it cannot be read on the host. The
     neighbor of each internal face is taken from libMesh while the worklist is built.

### Interpretation

- **Removing the host loop dominates at higher thread counts.** It was a fixed serial cost of
  about 135 ms at 2.1M cells. Kokkos assembly now scales 5.1x from 1 to 8 threads, up from 4.5x.
- **Slots gain less in MOOSE than in the mini-app** (1.15-1.6x on the flux matrix, against about
  2x there). In MOOSE the flux pass is still dominated by the parsed-coefficient evaluation (about
  40%, measured earlier) and the per-side datum construction. The next assembly gains are
  precomputed property arrays and computing each face once.
- **Assembly is now about 17% of a step** with the fast solver configuration, so the linear solve
  sets the step time again.
