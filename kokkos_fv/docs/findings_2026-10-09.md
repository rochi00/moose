# Findings: 2026-10-09, Kokkos linear FV baseline on the OpenMP backend

This summarizes the first day of measurements on the existing Kokkos linear FV implementation
(advection, diffusion, source, functor Dirichlet/Neumann BCs). Details and raw data are in
`kokkos_fv/bench/` (harness, `README.md`) and
`kokkos_fv/bench/results/RESULTS_2026-10-09_openmp_m4max.md`.

**Status of the proposed design.** None of the indexing and assembly strategies in
`kokkos_ns_linearfv_detailed_design.md` was implemented or measured today. Everything below
characterizes the **current** code. It is the baseline the new design will be compared against.

## 2. Framework changes made (on the branch)

1. **`framework/src/kokkos/systems/KokkosLinearSystem.K`.** Timing sections inside
   `computeKokkosLinearSystem`: `KokkosFVSyncToDevice`, `KokkosFVBoundaryData`,
   `KokkosFVElementalMatrix`, `KokkosFVFluxMatrix`, `KokkosFVElementalRHS`, `KokkosFVFluxRHS`,
   `KokkosFVSyncToHost`. Every dispatch fences, so these sections measure execution time.
2. **`framework/src/kokkos/base/KokkosMooseInit.K`.** If `KOKKOS_NUM_THREADS` is set, Kokkos uses
   that value instead of MOOSE's thread count.
   - **Reason:** linear FV variables forbid more than one MOOSE thread
     (`MooseLinearVariableFV.C:90`), so the OpenMP backend could only ever run one thread per rank.
   - Default behavior is unchanged.

## 3. Test harness (`kokkos_fv/bench/`)

- **Inputs.** `inputs/advdiff_kokkos.i` and `inputs/advdiff_cpu.i`: the same 3D
  advection-diffusion-source problem with Kokkos and CPU objects. Mesh size, element type and skew
  are set from the command line.
- **Repeated assembly.** A `Transient` executioner with no time-derivative kernel and a one-sweep
  solve (`l_max_its = 1`, Richardson/Jacobi, no norm).
- **`bench.py parity`.** CPU vs Kokkos matrix and RHS, entrywise, from PETSc binary dumps
  (`-ksp_view_mat`, `-ksp_view_rhs`). Mismatches are split into boundary and interior rows.
- **`bench.py determinism`.** Hash of the matrix and RHS over repeated fresh runs.
- **`bench.py sweep`.** Per-assembly time per PerfGraph section. Each case runs at two step
  counts and the times are differenced, which removes setup. `--set` overrides input parameters.

## 4. Correctness findings

### 4.1 CPU vs Kokkos parity

| Mesh | Result |
|---|---|
| Orthogonal hex (serial and 3 ranks) | Identical to round-off (max abs. difference 4e-16) |
| Skewed hex, tet, prism | **Every interior row matches**; differences only in rows of cells with a boundary face (up to about 10% relative) |

The boundary differences have two causes. The existing Kokkos tests use only 1D/2D orthogonal
meshes, so neither is visible there.

1. **Dirichlet distance.** `KokkosLinearFVFunctorDirichletBC` uses `|d_Cf|`
   (`KokkosLinearFVFunctorDirichletBC.h:47`). The CPU `LinearFVAdvectionDiffusionFunctorDirichletBC`
   uses `|d_Cf . n|` (`LinearFVBoundaryCondition.C:93`).
2. **Neumann face value.**
   - The CPU `LinearFVAdvectionDiffusionFunctorNeumannBC` adds a tangential-gradient term
     `grad(phi_C) . (d_Cf - (d_Cf . n) n)` to the face value used by advection, and requests cell
     gradients for it (`LinearFVAdvectionDiffusionFunctorNeumannBC.C:34`).
   - The Kokkos Neumann BC returns the cell value.
   - On the skewed hex mesh, all 57 right-hand-side-only mismatches are in cells next to the
     outflow (Neumann) faces.

**Semantic difference.** The Kokkos Neumann functor is a normal gradient. The CPU Neumann functor
is a diffusive flux divided by `k`. They coincide only for zero flux.

### 4.2 Bug

`KokkosLinearFVSource` cannot be used with its default `scaling_factor = 1`. The default builds a
`KokkosConstantFunction`, and the kernel requires a `KokkosParsedFunction`, so it fails with
"Kokkos function '1' is not of type 'KokkosParsedFunction'". The existing tests always set
`scaling_factor` explicitly, so they do not catch this.

### 4.3 Determinism (fresh process per run, 24^3 hex, 10 runs)

| OpenMP threads | Distinct matrix/RHS results |
|---|---|
| 1 | 1 |
| 4 | 10 |
| 8 | 10 |

The atomic accumulation in today's flux kernels makes threaded assembly non-reproducible. This
confirms the motivation for the atomic-free gather in the design (D7, H2c).

## 5. Performance findings (per assembly, 2,097,152 hex cells, 1 MPI rank)

| Section | Kokkos 1 thread | Kokkos 8 threads | CPU objects |
|---|---|---|---|
| Total assembly | 1555 ms | 347 ms | 1874 ms (includes 628 ms of gradients the Kokkos path does not compute) |
| Kokkos flux matrix | 1252 ms | 176 ms | - |
| Kokkos elemental RHS | 116 ms | 18 ms | - |
| Host linear FV loop with **no** CPU kernels attached | 141 ms | 134 ms | - |
| `MatSetValuesCOO` + sync | about 15 ms | about 12 ms | - |
| Peak memory per rank | 9.9 GB | 10.3 GB | 5.5 GB |

1. **The empty host linear FV loop is the largest fixed overhead.**
   - `ComputeLinearFVElementalThread` / `ComputeLinearFVFaceThread` walk every element and face
     even when every kernel is a Kokkos object: about 135 ms per assembly.
   - It runs serially and caps thread scaling.
   - With constant coefficients at 8 threads, it costs more than all the Kokkos work combined
     (136 vs 132 ms).
   - **Fix:** skip the host loops when the system has no non-Kokkos linear FV objects.
2. **The flux-matrix pass dominates the Kokkos work** (80% on 1 thread).
   - Evaluating the parsed coefficient (device RPN interpreter) is about 40% of that pass. It runs
     4 times per face: twice per directed side, two directed sides per face.
   - With constant coefficients, assembly is 1.6x faster on 1 thread and 1.3x on 8 threads.
   - This supports precomputed property arrays (D10), the compute-once face pass (D7), and the
     combined matrix + RHS hook.
3. **The Kokkos passes scale well with threads.** The flux matrix speeds up 7.1x from 1 to 8
   threads. Total assembly speeds up only 4.5x, because of finding 1.
4. **Memory.** Kokkos uses about 1.8x the CPU path's memory: about 2.1 KB per cell extra, counting
   host plus "device" copies, which are separate allocations on this backend. This needs breaking
   down before GPU sizing.
5. **The solve is negligible in the harness** (under 4% of assembly), as intended.

The CPU column is a reference point, not a fair speedup baseline: the CPU path also computes the
gradients its Neumann BC needs.

## 6. Implications for the design

| Finding | Design item | Effect |
|---|---|---|
| Empty host loop costs about 135 ms | R9 (CPU object policy), section 10 of the detailed design | Add: skip host loops when all objects are Kokkos. A cheap, immediate win. |
| Parsed coefficient is about 40% of the flux pass | D10 (property arrays), D7 (compute once per face) | Supported |
| Atomics make threaded assembly non-reproducible | D7 / H2c (gather) | Supported |
| Boundary discretization differs from the CPU on non-orthogonal meshes | Parity criteria (12.2 of the detailed design) | Decide whether Kokkos BCs should match the CPU (`|d_Cf . n|`, tangential Neumann term) before porting NS BCs |
| Kokkos memory about 1.8x the CPU path | P12, memory budget (3.7 of the detailed design) | Break down per structure; feeds the layout experiments |

## 7. Layout mini-app: first measurements of the proposed design

Standalone Kokkos benchmark `kokkos_fv/bench/miniapp/fv_layout_bench` on MOOSE-dumped meshes.
Full results are in `kokkos_fv/bench/results/LAYOUT_RESULTS_2026-10-09_openmp_m4max.md`.

**Correctness:**
- A replica of today's scheme (V0) reproduces MOOSE's Kokkos matrix and RHS exactly on orthogonal
  hex, and to about 1e-15 on tet and skewed hex.
- All new variants match V0 to at most 6.6e-16.

**Per-assembly time, 2.1M hex cells:**

| | Today's scheme (V0) | + face SoA (V1) | + precomputed slots (V2) | gather, per-face scratch (V3) | gather, half-face scratch (V4) |
|---|---|---|---|---|---|
| 1 thread | 129.5 ms | 1.25x | 2.47x | **2.77x** | 2.51x |
| 8 threads | 17.6 ms | 1.21x | **2.36x** | 1.48x | 1.28x |
| Deterministic with threads (skewed hex, tet) | no | no | no | **yes** | **yes** |

**Findings:**

- **Precomputed slots give most of the gain** over today's scheme: 2.4x on hex and up to 2.2x on
  tet with RCM. They work by removing the binary search.
- **Face SoA halves the indexing/geometry memory** (528 → 280 B/cell on hex) but is not faster by
  itself.
- **The gather is deterministic and beats today's scheme.** On the CPU at 8 threads it loses to
  the atomic + slots variant, because CPU atomics are cheap. Atomics vs gather has to be decided
  on a GPU.
- **Half-face scratch did not beat per-face scratch** on the CPU.
- **Ordering:** scrambled numbering slows the new layouts 2.5-4.5x. RCM numbering plus
  owner-sorted faces recovers this on hex and gives 2x on tet. Renumbering without re-sorting
  faces hurts.
