# Findings: 2026-10-14, device PETSc types, per-assembly overhead, coefficient cache, Kokkos threads

Continues `findings_2026-10-12.md`. All runs: MOOSE `rc/kokkos_moose_navier_stokes` (`--with-kokkos=cpu`,
conda env `moose-next`), Apple M4 Max, 1 MPI rank. GPU behavior is not measured here.

The changes follow the GPU campaign's conclusions. The GPU run found that keeping the matrix and
vectors on the device matters most. Next came a fixed host overhead of about 2 ms per assembly,
and then the coefficient evaluations in the flux kernels.

## 1. Changes

1. **Device PETSc types by default (GPU builds only).**
   - `LinearSystem::selectKokkosPetscTypes()` is called from `FEProblemBase::init()` when MOOSE
     is built with `MOOSE_ENABLE_KOKKOS_GPU`. It applies when every linear FV object of a linear
     system is a Kokkos object.
   - It adds `-<sys>_mat_type aijkokkos` and `-vec_type kokkos` to the problem PETSc options.
     MOOSE applies these to the existing matrices and vectors when it inserts the options before
     the first solve.
   - **Setting them in the PETSc database at init does not work.** MOOSE clears that database
     before the first solve, and the vectors then change type underneath the run (segfault).
   - **Nothing is added if the input or the command line sets this system's matrix type or a
     vector type other than `kokkos`.** Selecting only one of the two crashed: a Kokkos matrix
     with host vectors.
   - With several Kokkos linear systems, each adds its own matrix type and they share
     `-vec_type kokkos`.
   - Matrix types must use the system-name prefix: MOOSE rejects an unprefixed `-mat_type`.
2. **Per-assembly overhead removed (linear FV only).**
   - **Fence once per assembly.** `Dispatcher::parallelForAsync()` dispatches without a fence,
     and linear FV kernels and BCs use it. `computeKokkosLinearSystem()` fences once, in the new
     `KokkosFVWait` section, before PETSc reads the results. `parallelFor()`, used by Kokkos FE
     objects, still fences after every dispatch.
   - **Cached tag arrays.** The kernel copy made for each dispatch used to rebuild its tag arrays
     from the tag sets: two device allocations and copies per dispatch. The original object now
     keeps the arrays and rebuilds them only when its tag sets change; copies share them.
   - **Shared scalar storage in the parsed-function evaluator.** The evaluator copy made for each
     dispatch allocated four device arrays, copied them over with a fence, and freed them. Copies
     of an evaluator that reads only constants, coordinates, time and scalar symbols now share the
     original's scalar array and refresh only values that changed. Expressions with fields,
     material properties or functions keep the old behavior. This code is shared with Kokkos FE
     objects.
3. **Per-side coefficient cache in flux kernels.**
   - New optional hook `computeFaceCoefficient(datum)`. A pre-pass evaluates it once per
     interior and boundary side per assembly into a device array indexed by (side, element). The
     contribution hooks read it through `faceCoefficient(datum)`; hook signatures are unchanged.
   - `KokkosLinearFVDiffusion` uses it. The parsed diffusion coefficient is now evaluated 2 times
     per interior face instead of 4: once from each side, instead of once per matrix entry from
     each side.
4. **Kokkos threads independent of MOOSE threads.** See section 6.

## 2. Where the per-assembly overhead came from

**Method.** A Kokkos Tools library (`bench/tools/kokkos_event_counter.cpp`) counts allocations,
fences and launches, grouped by the first MOOSE frames of the call stack. Per-assembly counts come
from runs with 2 and 12 assemblies (difference method). The input is `advdiff_kokkos.i` with
n = 8 and 1 thread.

| Per assembly | Before | After |
|---|---|---|
| Device allocations (and frees) | 26 | 3 |
| Fences | about 220 | 54 |
| Kernel launches | 14 | 16 (two coefficient loops added) |

- **Where the 26 allocations came from:** 12 from rebuilding the tag arrays and 9 from parsed
  evaluator copies. The rest come from `System::setActive*Tags`.
- **Where the fences came from:** each dispatch fenced explicitly. In addition, the evaluator and
  tag-array copies fenced on copy-in and on destruction.
- **Before the fix the tool reported 276 fences.** About 56 of those came from Kokkos fencing
  around every kernel while a tool is loaded. The counter now opts out of that
  (`requires_global_fencing = false`); the "before" figure subtracts 4 per launch.
- **What remains:** the 3 allocations and most of the 54 fences are in `System::sync` and the
  `setActive*Tags` calls. That code is shared with Kokkos FE assembly and was left unchanged. It
  is the next target if the GPU still shows host overhead.
- The allocation count matches the GPU profile's 22 allocate/free pairs per assembly. The fence
  count is not comparable: the GPU count was of device synchronizations.

## 3. Steady assembly (hex, 3 repeats, difference method)

Before is `sweep_20261012-114349.csv` (precomputed slots, host loop skipped). After is
`sweep_20261014-091251.csv`.

| Cells | Threads | Assembly before → after | Speedup | Flux matrix + coefficients before → after |
|---|---|---|---|---|
| 33k | 1 | 14.8 → 11.2 ms | 1.32x | 12.4 → 9.0 ms |
| 33k | 8 | 3.6 → 3.0 ms | 1.20x | 2.5 → 1.9 ms |
| 262k | 1 | 119.7 → 90.8 ms | 1.32x | 102.1 → 73.3 ms |
| 262k | 8 | 23.5 → 18.6 ms | 1.26x | 18.5 → 13.3 ms |
| 2.1M | 1 | 946 → 717 ms | 1.32x | 817 → 589 ms |
| 2.1M | 4 | 300 → 218 ms | 1.38x | 250 → 173 ms |
| 2.1M | 8 | 187 → 134 ms | 1.39x | 153 → 102 ms |

- **The gain is the coefficient cache.** At 2.1M cells and 1 thread, the flux matrix pass drops
  from 817 to 236 ms, and the new coefficient pass costs 353 ms. Evaluating the parsed function
  still dominates, now in one place.
- **Fence removal does not show up on the CPU backend.** OpenMP dispatches are synchronous, so
  each fence was nearly free. The fence and allocation savings are for the GPU, where the
  campaign measured about 2 ms per assembly.
- **Parity is unchanged.** All 16 cases shared with the 2026-10-12 `bench.py parity` run have
  identical metrics (within 1e-14). Interior rows match the CPU implementation to round-off; the
  known boundary differences on non-orthogonal meshes are unchanged.

## 6. Threading

- **Why host linear FV runs on one thread.** `MooseLinearVariableFV` errors when the app has
  more than one MOOSE thread. The check was added on 2024-03-19 (`29466175a5`), removed on
  2024-05-05 (`2c1e0870f3`), and restored the next day (`9aba8bdb34`), which also limited the
  navier_stokes linear-segregated tests. The about 75 `max_threads = 1 # see libmesh issue #3808`
  test limits follow from that error.
- **The cause is libMesh issue #3808 (open).** `PetscVector::operator()` caches the PETSc array
  pointer, and `set()`/`add()`/`close()` invalidate that cache. Both steps take a mutex, but the
  read through the cached pointer happens after it is released, so another thread's write can
  invalidate the pointer first. Debug builds then fail the assertion `local_index < _local_size`;
  optimized builds can silently read stale data.
- **Status of the host code.** The gradient loops no longer use those calls (#32999), but
  `MooseLinearVariableFV::getElemValue()` still reads with `operator()`. It is reached through
  functor evaluation in kernels, BCs, aux kernels and postprocessors.
- **The host code is unchanged.** Per the decision on 2026-10-14, only Kokkos linear FV gains
  threading.
- **Kokkos assembly does not use those calls.** It takes the PETSc arrays once per assembly and
  writes with atomics into its own arrays. Its threading only needed a way to set the thread
  count.
- **New option `--kokkos-threads=<n>`.** It sets the thread count of the Kokkos host backend.
  Precedence: `--kokkos-threads`, then the `KOKKOS_NUM_THREADS` environment variable, then
  `--n-threads`. Kokkos's own `--kokkos-num-threads` flag is not passed to Kokkos by MOOSE, and
  PETSc reports it as unused.
- **Measured effect.** At 262k cells, Kokkos assembly over 6 steps takes 0.576 s with 1 thread
  and 0.121 s with 8 (0.124 s with `KOKKOS_NUM_THREADS=8`).
- **New tests.** 2D diffusion with mixed Dirichlet and Neumann BCs (second order) and 1D
  advection-diffusion (first order), both MMS with `--kokkos-threads=4`, CPU only. They check
  convergence order rather than exact output, because the order of atomic additions can change
  results at round-off.

## 9. Green-Gauss gradient variants (mini-app, CPU)

Full results: `bench/results/GRADIENT_RESULTS_2026-10-14_openmp_m4max.md`
(`gradient_20261014-102129.csv`). Four variants, all checked against a serial host reference
(at most 8.4e-14 relative):
- **G0:** per-cell gather over padded per-(side, cell) data.
- **G1:** per-cell gather over the face SoA through `elem_faces`.
- **G2:** per-face atomics plus a volume pass.
- **G3:** per-face atomics with 1/V folded in.

| Result | Detail |
|---|---|
| Gathers beat atomics | 1.5-1.8x at all thread counts with native or RCM numbering. G2 and G3 gave 13-20 distinct results over 20 passes on the skewed hex and the tet. |
| G0 is fastest on the CPU | 1.0-1.4x faster than G1, for example 2.84 against 3.13 ms (skewed hex 2.1M, 8 threads), at 432 against 280 B/cell |
| G1 needs good numbering | 7-12x slower with scrambled numbering; G0 only about 2x |
| Cost | About 3 ms per gradient at 2.1M cells and 8 threads: about 2% of today's MOOSE Kokkos assembly |

The CPU favors G0's contiguous per-cell side data. The design goals favor G1's single face array.
Which wins on a GPU depends on coalescing, which the CPU cannot show. The GPU run should add
cell-fastest variants of both (see the results file).

**Second sweep** (`gradient_20261014-104545.csv`, details in the results file):
- **Cell-fastest and SoA layouts are slower on the CPU.** G0C, G0 with cell-fastest padded arrays,
  is about 2x slower than G0. G1C, with cell-fastest `elem_faces`, is about 10% slower than G1.
  G1CS, with SoA geometry, is a further 15-20% slower.
- **These are the layouts that coalesce on a GPU,** so the ranking may flip there (Q12).
- **Morton numbering with owner-sorted faces** performs the same as native and RCM numbering on
  the generated meshes.

## 10. Fused face pass (mini-app, CPU)

`fusion_20261014-110913.csv`: V2 against V2F, which computes the diffusion and advection terms of
a face in one kernel, so each matrix entry gets one atomic add per face instead of one per kernel.
3 processes, 20 passes each.

| Mesh | Threads | Order | V2 face pass | V2F face pass | Speedup |
|---|---|---|---|---|---|
| hex 2.1M | 1 | native | 49.8 ms | 31.3 ms | 1.59x |
| skewed hex 2.1M | 8 | native | 10.9 ms | 6.86 ms | 1.59x |
| skewed hex 2.1M | 8 | rcm/owner | 8.17 ms | 5.33 ms | 1.53x |
| tet 1.5M | 1 | rcm/owner | 26.1 ms | 16.3 ms | 1.60x |
| tet 1.5M | 8 | rcm/owner | 4.35 ms | 2.60 ms | 1.67x |

- **Fusion is 1.5-1.65x faster in every configuration.** The one outlier, 2.2x (tet, 8 threads,
  native numbering), had a 46% spread across processes.
- **Results are unchanged:** V2F matches V0 to at most 7e-16 relative. Both atomic variants still
  give different results from pass to pass on the skewed hex and the tet with 8 threads.
- **Fusion is therefore worth having on the CPU.** The GPU campaign checks it there (Q13), where it
  also halves the launches.
